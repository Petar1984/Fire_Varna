# Amendment of 2026-09-15 to the submission contract — a sixth report type that never enters the map pipe

**Amends:** `docs/audits/backfill_and_submission_extension_plan_20260509.md` (the contract of 2026-05-09, ratified by Petar) and `docs/audits/амандамент_подаване_13.09.md` (one standard for every report made at a hydrant).
**Status:** signed by Petar on 15.09.2026 at Gate 1 of лот О of the theme „Проблемите“ (his words: „нека е в публичното — действаме според препоръките“; „подписвам но да внимаваме да не счупим нещо работещо и да не създадем проблеми и бъгове“). Written by the Architect; the plan is `docs/plans/ПЛАН_Проблемите_лотО_обратна_връзка_15.09.md`.
**Trigger:** backlog rows F-14 and F-8…F-13 (12.09): the only channel a colleague has for a problem WITH THE APP is the note box of a hydrant report — five such notes stand in the moderation log, none of them publishable, all of them about the app (offline uncertainty, the form without a type picker, a literal `\n` on the map). Petar's frame (15.09): not free text but a template — the kind of problem in one tap, the context collected by the app itself, one sentence only where a sentence is the content (an idea, „other“) — so that a later AI cycle can reproduce the problem without asking the colleague.

## 1. What this amendment adds to the contract

| Contract area | Old rule | New rule |
|---|---|---|
| § Report types — five kinds, all about a hydrant | `exists_confirmed`, `missing`, `new_hydrant`, `wrong_location`, `damaged` | a **sixth** kind, `app_feedback`, about the APP; it is a report in shape (same modal, same YAML head, same Worker) and NOT a report in meaning (no hydrant, no coordinate, no location method, no canonical field) |
| YAML head — fixed key order | sixteen keys | **two new keys** after `description`: `feedback_kind` (one of `address`, `report`, `map`, `freeze`, `idea`, `other`) and `feedback_context` (**a flat JSON string on one line** — the Worker reads the head line by line, so no nested YAML) |
| `reporter` | required, 2–50 characters, printed in the issue | for `app_feedback` **null by design**: the repository is public and a name adds nothing to an app problem; the name field is not rendered and the 2–50 check is skipped for this type only |
| Coordinates | `expected_coord` / `reported_coord` per type | for `app_feedback` **always null**, and `location_method` null too (v1.1); a search that the app itself parses as a coordinate (any shape `parseCoordQuery` accepts: decimal pairs with any precision, comma pairs, degrees-minutes-seconds, `geo:` URIs, map links) is recorded as `[координати]` in the query AND in the row titles the moment the GPS row is drawn, and the context builder masks the same shapes once more (v1.1, after Gate 2 found the GPS row's title carrying the coordinate) |
| Labels | `report`, `<type>`, `pending-review` | for `app_feedback` **`app-feedback`, `fb-<kind>`, `pending-review` and never `report`** |
| 422 on a label the repository does not know | retry once without labels | for `app_feedback` **never retried without labels**: the report is queued locally and the colleague is told; the queue keeps it on a later 422 as well (v1.1 — until then a reload dropped it with a console line); the labels are a precondition Petar creates by hand (`app-feedback`, `fb-address`, `fb-report`, `fb-map`, `fb-freeze`, `fb-idea`, `fb-other`) |
| Client `applyReports` (the map's optimistic note) | any report with a resolvable `hydrant_id` may write its text into the live note | **an allowlist of the five hydrant types** is checked before any note is written; a type outside it never touches a hydrant |

## 2. The four consumers of the issue stream and the guards (measured at 758f35e; the fourth found at Gate 2)

1. **The Worker fetches only `labels=report`** (`worker/index.js:325-330`): an issue labelled `app-feedback` is never returned to the map's poll nor to the ingest's fetch. The Worker's POST forwards labels verbatim and validates no `report_type` (`:164-171`) — nothing in the Worker changes.
2. **The ingest skips an unknown type** as `not_a_hydrant_report` with zero data changes (лот 6, commit `6ced4e6`; `scripts/lib/hydrant_core.py`, `KNOWN_REPORT_TYPES`) — if a feedback issue ever gained the `report` label by hand, it would still change nothing.
3. **The client refuses to write a note** for a type outside its allowlist (`applyReports`, this amendment) — the one path the first two guards did not cover.
4. **The reports dashboard** (`scripts/build_reports_dashboard.py`) fetches every issue without a label filter and counted any body with a `report_type`; from v1.1 it keeps the five hydrant types only and prints how many feedback issues it skipped.

## 3. The context (what the app sends, by kind)

Common to every kind: `app_version`, `online`, `device` (platform and browser family only — no model, no build), `screen`, `mode` (near / top / all), `basemap` (osm / pmtiles, satellite on or off), `release` (the first twelve characters of `ADDRESS_QUARTERS_SHA256` — the page does not read the generation manifest), `worked_before` (optional: worked before / never worked / unknown; absent for an idea, where it has no meaning). Per kind: **address** — the last query (masked if it looks like a coordinate), how many rows the dropdown showed, the first row's title, the row the colleague tapped (title, never a pin); **report** — the last report type opened, the last recorded error, how many reports wait in the offline queue; **map** — the active hydrant's public id, the zoom, the number of points; **freeze** — the last recorded error, the service worker state, the device memory class; **idea / other** — where the colleague was (map / search / building panel). Never: a GPS fix of the colleague, a reporter name, a stack trace, the queue's contents, a screenshot.

The two recorders behind this are the only always-on cost of the lot: one line for the last uncaught error (message, file basename, line — no stack) and one record of the last search drawn by the dropdown (query, rows shown, first row, tapped row), kept by an observer OUTSIDE `initAddressSearch` because ADR 006 D12 makes every function inside it untouchable. Declared gap: a row chosen with Enter is not recorded.

## 4. Acceptance (the gates of the plan, §3)

- The „+“ menu shows six entries, the long-press menu at a hydrant shows four — the sixth exists only where there is no hydrant.
- Six tiles; the context box is rebuilt on every tile with that kind's keys; the sentence is required only for `idea` and `other`; no name field.
- The issue head carries `feedback_kind` and a parseable `feedback_context` with no `lat` / `lon` / `coords` key and `reporter: null`; the sentence appears exactly once in the body; the labels never contain `report`.
- A coordinate-looking query is masked; two different sentences from one person are two reports (`dedupHash`); the 30 s throttle stays.
- The five old branches of the form, the four hydrant labels and the ingest are byte-equal to the base; the full suite keeps every test of the base and adds the lot's own; four negative halves fall for their own reason.

## 5. What this amendment does not decide

The AI cycle that reads `app-feedback` issues, replays address queries through `tests/address_slice_probe.mjs` and triages ideas into a board for Petar is a separate lot after the first real reports (Р9). A private repository for feedback was considered and rejected by Petar (15.09): same repository, anonymous. The Worker, the ingest, `data/`, `sw.js` and the places search are untouched.
