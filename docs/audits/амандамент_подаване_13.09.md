# Amendment of 2026-09-13 to the submission contract — one standard for every report made at a hydrant

**Amends:** `docs/audits/backfill_and_submission_extension_plan_20260509.md` (the contract of 2026-05-09, ratified by Petar).
**Status:** signed by Petar on 13.09.2026 at Gate 1 of лот 1 of the theme „Проблемите“, after he tested the change locally (his words: „искам да е със звездичка“, „искам всички да са един стандарт“, „добави ги“, „давай да вкарваме поправката в живата карта“). Written by the Architect; the Executor does not edit this file.
**Trigger:** issue #769 — the reporter wrote that neither on the hydrant itself nor before moving its location could he mark whether it works. Two gaps in one note: the operational picker was hidden for every record that already carried a status, and the wrong-location form carried no type and no operational answer at all (also #716, #731). The moderation log recorded it in cycle #35.

## 2. The standard (all three forms made at an existing hydrant)

Applies to `exists_confirmed`, `wrong_location` and `damaged` (`AT_HYDRANT_TYPES` in `index.html`; the block is `hydrantPickersHTML`):

1. **Type picker** („Тип хидрант“) — always shown, **required**, pre-selected from the record when the record carries a type (the record stores the picker's own vocabulary: `надземен` / `подземен`), so confirming is one tap and correcting is one tap.
2. **Operational picker** („Работи ли?“) — always shown, **required**, **never pre-selected**. The record stores `works` / `not_working` / `not_tested` while the picker offers `да` / `не` / `не съм проверявал`; a status is a dated observation, not a property. When the record carries a status it is shown as a readable label above the row: „сега: “ + `OPERATIONAL_LABELS[value]` (Работи · Не работи · Не е тестван). `не съм проверявал` is a valid answer — nobody is forced to invent a test result.
3. The form-specific fields follow the block unchanged: the optional note (`exists_confirmed`), the description and the real location (`wrong_location`), the damage description (`damaged`).

Why required for every record (Petar, 13.09): one form for everyone; the earlier proposal to make the answer optional for records that already carry a status was rejected by him at the local test.

## 3. What changes in the code (the write-set of лот 1)

- `index.html`: `hydrantPickersHTML`, `AT_HYDRANT_TYPES`, the three branches of `typeFieldsHTML`, the defaults in `showReportModal` (the `damaged` default „не съм проверявал“ is removed — nothing is pre-selected), the validation in `onSubmitClicked` (one block for the three forms and `new_hydrant`), the canonical fields in `buildReportObject` (`type` and `operational_status` for the three forms and `new_hydrant`), and the optimistic local patch `reportTypeToSemanticPatch` (merges both fields for the three forms).
- `scripts/lib/hydrant_core.py`: `apply_wrong_location` applies `type` and `operational_status` when they are canonical values, **after** the re-key of the record, so the provenance lands under the new id; `apply_damaged` applies `type` as well as `operational_status`. Both keep ignoring `null` / missing / non-canonical values.
- Nothing else: `missing` keeps no canonical fields (a missing hydrant has nothing to test); `new_hydrant` already carried both; the YAML key order already contains `type` and `operational_status`; the Worker is a pass-through that normalises both fields for every issue; the labels, the offline queue and `data/` are untouched (zero bytes in `data/` at delivery).

## 4. Acceptance (replaces the superseded rows)

- Open `exists_confirmed` / `wrong_location` / `damaged` on a record **with** a status: both pickers present, both marked required, no operational chip selected, the label shows the stored status, the type chip of the record is pre-selected.
- Open the same forms on a record **without** a status: both pickers present and required, no label.
- Submit without an operational answer → blocked („Моля попълни задължителните полета“); with `не съм проверявал` → allowed.
- Payload: `type` and `operational_status` canonical for the three forms; `null` when the picker is untouched (not reachable through the form, reachable through old issues).
- Ingest: a `wrong_location` report carrying both fields changes coords, id, `existence_status`, `type`, `operational_status`; the old values are in provenance under the **new** id; a report without them changes only coords / id / `existence_status`, exactly as before. A `damaged` report without answers no longer downgrades a known status (the silent pre-selection is gone).

## 5. Reading old issues

Issues created before this amendment carry `type: null` and `operational_status: null` for `wrong_location`, and `operational_status: not_tested` from the old pre-selection for `damaged`. The ingest treats `null` as „no observation“ (only values in `CANONICAL_TYPES` / `CANONICAL_OPERATIONAL` are written). Old `damaged` issues that are still open are moderated one by one, as always.

## 6. Declared consequence and its guard

With the operational question visible and required on every form, a colleague who has not tested a hydrant will answer `не съм проверявал`. On a record that already carries `works` or `not_working` this writes `not_tested` at ingest — a downgrade without a new observation. Petar's decision (Р7(i), 13.09): accepted, recorded here; the guard is moderation — every report is approved by his hand before ingest, and the moderation board shows the old and the new value. Immediately after submission every pin is yellow („докладван“) for everyone; the colour changes only after approval, ingest and a new build of `data/`.
