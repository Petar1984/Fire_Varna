# ADR 005 — Service-worker cache lifecycle (offline shell, pack retention, update discipline)

- **Status:** Proposed — awaiting Petar (Gate 1)
- **Date:** 2026-08-11
- **Authors:** Petar (decision authority), Claude Code (Planner draft; adversarial input from an external Kimi audit, 11.08.2026, re-verified line-by-line in the worktree)
- **Amends:** ADR [`002_osm_pmtiles_basemap_offline.md`](002_osm_pmtiles_basemap_offline.md) D4 (offline strategy) and D5 (cache versioning). Does **not** supersede it; D1-D3, D6-D8 stand unchanged.
- **Ground inputs (measured, constraining — `scratch/sw_fix_facts.md`):** GitHub Pages header traces (Sol, urlscan 08.03.2026 and 20.05.2026), the W3C service-worker update rules (CR draft 04.08.2026), and two documented versioned-asset traps (Cloudflare 03.07.2026 404 class; `?v=` unreliability through intermediaries). - **Execution plan:** [`docs/plans/sw_cache_lifecycle_fixes.md`](../plans/sw_cache_lifecycle_fixes.md)

## Context

ADR 002 D4/D5 decided *what* is cached (shell + hydrants + search + basemap) and *how caches are named* (`basemap_version` in every name), but never decided the **lifecycle**: when a cached entry is refreshed, when an old cache may be destroyed, and which worker may serve which page. `sw.js` (281 lines, first service worker in the app, registered only when the PMTiles capability is active — committed flag `false`) implements three consequences of that gap:

1. **The offline shell never refreshes.** `navigationHandler` (`sw.js:205-214`) is network-first but never writes back; `index.html` enters `CACHE_CORE` only in `install` (`sw.js:85-86`), which runs only when `sw.js` bytes change. The data caches meanwhile refresh on every online use (`sw.js:191-193`, `216-229`). Offline, a months-old shell parses fresh-schema data.
2. **A version bump destroys the user's opt-in download.** `activate` (`sw.js:99-111`) deletes every non-current B2 cache, including `fire-varna-basemap-<old>` (the ~5.75 MB `varna_basemap.pmtiles` fetched only on explicit opt-in, `sw.js:127-149`) and `fire-varna-offline-pack-<old>`. No notice; the user discovers it offline, at an incident.
3. **A post-deploy version-mix window.** `skipWaiting()` (`sw.js:92`) + `clients.claim()` (`sw.js:109`) let a new worker take over a page still running the HTTP-cached old `index.html`, whose hardcoded `BASEMAP_VERSION` (`index.html:4508`, used at `4599`) requests old-version asset URLs the new worker's routes do not match (`sw.js:197`, `243-247`). `index.html` and `sw.js` deploy atomically and carry the **same measured** `Cache-Control: max-age=600` (Pages, measured 08.03.2026 / 20.05.2026). What differs is their *effective* lifetime: a navigation honours the HTTP cache, while the worker update check bypasses it (Chrome 68+; any registration older than 86,400 s is forced to `no-cache` by spec). So a fresh worker can pair with a stale shell for ~10 minutes — and, because an `index.html` change never triggers an install (update = byte-compare of `sw.js` only), the pairing can outlast that window if nothing else changes.

Zero live users are affected today (the worker is never registered while the flag is false and no sticky override is set), which is precisely why this is the moment to fix it: **these are pre-conditions of any future flag flip.**

## Decision

- **D1 — The cached shell is refreshed by use, not by worker version.** A successful online navigation (HTTP 200, not redirected, `text/html`) is written into `CACHE_CORE` under the literal key `index.html` inside `event.waitUntil`. Shell and network-first data can no longer drift apart. Quota failures are non-fatal.
- **D2 — Deletion of an opt-in download is deferred, bounded, and announced.** `activate` retains exactly **one** previous generation — the old `fire-varna-basemap-*` cache that holds a pmtiles entry plus the `fire-varna-offline-pack-*` cache of the same version — and prunes it only when the current-generation pack is **confirmed installed**, or on the existing `?basemap_pmtiles=0` full revert. Old `fire-varna-core-*` caches are always deleted (a stale shell is defect 1). Measured cost: two generations = ≈ 11.0 MB of pmtiles **total** (2 × 5,748,578 B), i.e. **+5.75 MB incremental** over one pack. A failed install — quota or otherwise — **deletes nothing**: the worker reports `offline-pack-error { quota, retained }` and the retained generation stands. It is dropped only on an explicit user act (`prune-retained-pack`, which prunes and immediately retries the install in the same handler) or on the `?basemap_pmtiles=0` revert. The `/quota/i` error heuristic (`sw.js:141-142`) may only choose the wording of a message — never authorize a deletion.
- **D3 — Version-agnostic *lookup*, never version-agnostic *content*.** Cache-first, the network-first offline fallback, and the PMTiles Range handler search the current cache first and then the other caches sharing the same B2 prefix, matching by **exact URL**. Because the version is in the path, an old-version request can only ever be answered with old-version bytes — ADR 002 D5's "a stale basemap and a fresh app shell can never mix" is preserved at the byte level. The global `caches.match()` is forbidden: it would reach the PROTECTED search namespaces.
- **D4 — A new worker does not seize pages it did not install for.** `skipWaiting()` and `clients.claim()` are removed; a new worker waits for the old clients to go away, as the platform intends. This removes **takeover of already-open clients**; it does *not* remove every shell/worker mismatch — a **fresh** navigation inside the measured 600 s HTML window still pairs the new worker with a stale cached shell, because an `index.html` change never triggers an install and the navigation honours the HTTP cache. That residual is covered by D1 (the shell self-heals on the next online navigation), D2/D3 (old-version URLs stay servable from cache) and D7 (old-version URLs stay fetchable from the origin). Registration stays `register('sw.js')` with no options (`index.html:4683`): the default `updateViaCache: 'imports'` keeps the main script always revalidated, Chrome 68+ bypasses a fresh HTTP cache for the update check, and a registration older than 86,400 s is forced to `no-cache` — this deliberate default is what makes propagation bounded without extra machinery; introducing `importScripts` or an explicit `updateViaCache` must revisit this ADR. Accepted cost: a worker fix reaches an existing device only after all its tabs close. Data freshness is unaffected — hydrants/search stay network-first — so the wait delays only worker code and basemap generation, which is exactly what must move in lockstep with the shell.
- **D5 — An outdated pack, and any deletion of a downloaded pack, is a user-visible, opt-in event.** `offline-pack-status` carries `outdated`; `offline-pack-error` carries `retained`; `activate` broadcasts `offline-pack-outdated`; the page may post `prune-retained-pack`, which is the **consent act** for deleting the retained generation (the worker prunes, then retries the install in the same handler). Four reviewed Bulgarian strings back this contract, one of which names the deletion explicitly. The page surfaces a Bulgarian re-download control (≥ 44 px touch target) in the basemap selector; re-download remains an explicit opt-in action (ADR 002 addendum П2) and is never automatic on mobile data.
- **D7 — A retired basemap version stays in the deployed tree for at least one deploy.** Client-side retention (D2/D3) only helps a client that already holds the old cache. An old HTML page whose worker never cached the pack — or a client that is uncontrolled, or has no worker at all — still fetches `data/basemaps/<old>/…` from the origin, and such requests keep arriving for ~10 minutes after a deploy (measured `max-age=600`; Cloudflare-documented 404 class, 03.07.2026). Therefore, at a `BASEMAP_VERSION` bump the previous `data/basemaps/osm_varna_<old>/` directory MUST remain in the tree for at least one further deploy; `data/basemaps/basemap_manifest.json` gains `previous_version` at that bump; the retired directory is deleted only in a later, separate commit. Versioning stays **in the path** — query-string versioning (`?v=`) remains forbidden as unreliable through intermediaries (repo-verified: zero `?v=` occurrences in `*.html|js|json|py` today). The bump itself is out of scope here; this ADR lands the policy and the gate that permits it — `tests/test_basemap_manifest.py` moves from *exactly one* version dir to *current + at most one retired, declared as `previous_version`* (renamed accordingly, since the old gate name would otherwise assert a rule this ADR repeals).

- **D6 — Unchanged invariants.** `PROTECTED_CACHES` (`fire-varna-search-v2`, `fire-varna-approx-addresses-v1`) are never read across, never deleted; cross-origin requests are never intercepted; heavy downloads happen only on an explicit page opt-in; `BASEMAP_PMTILES_ENABLED` stays `false` and the flip remains a separate signed step (STOP B2).

## Alternatives considered

| Rejected | Why |
|---|---|
| Key `CACHE_CORE` to an app version and refresh network-first | Adds a second version axis and a build step this static repo does not have; D1 achieves the same with one write-back. |
| Force-revalidate navigations (`cache: 'no-cache'`) to defeat the HTML TTL | Reconstructing a `navigate` request changes redirect semantics and a redirected response cannot be returned to a navigation; adds latency on flaky mobile links. The mix window is closed by D3+D4 instead. |
| Migrate old pack bytes onto the new version's URL | Serves old tiles under a new version identity — the exact mixing ADR 002 D5 forbids. |
| Prompt the user *before* deleting the old pack, as the routine bump policy | A deletion that already happened cannot be undone offline; retention (D2) is strictly safer and costs +5.75 MB incremental. (The quota path is the one place where deletion is the only way forward — there it happens **only** after explicit consent.) |
| Auto-prune the retained pack on `QuotaExceededError` and retry | Deletes without consent *and before* the replacement is confirmed: if the retry also fails the user has **neither** pack — exactly the harm this ADR exists to prevent. The quota signal itself is a `/quota/i` string match (`sw.js:141-142`) that can misfire on a mislabeled network error. Replaced by the explicit consent act in D2/D5. |
| Query-string versioning (`?v=`) instead of a retained directory | Documented as unreliable through intermediaries (AWS/Cloudflare); the repo already versions in the path only (zero `?v=` today), and D7 keeps it that way. |
| Delete the retired version directory in the same deploy as the bump | That *is* the Cloudflare-documented 404 class: HTML from version A, HTTP-cached for ~600 s, requesting an asset the new deploy no longer contains. D7 keeps N and N−1 for one deploy. |
| Keep `skipWaiting` and rely on version-agnostic routing alone | Treats the symptom. Only D4 removes the class of "a worker serves a shell it disagrees with". |
| Add an "update ready — restart the app" UI to offset D4's latency | New UI surface + wording gate for zero benefit while the flag is false; revisit if field pilots show pinned workers. |

## Consequences

**Positive:** the offline shell can no longer freeze against fresh data; an explicitly downloaded offline pack survives a version bump, is never deleted without consent, and its replacement is announced in Bulgarian; the post-deploy mix window no longer leaves a **pack-holding** client with a dead basemap (D2+D3), and D7 keeps the same window survivable for clients that hold no pack, are uncontrolled, or are online-only; every rule is asserted by static gates in `tests/test_basemap_manifest.py`.

**Negative / accepted:** ≈ 11.0 MB of pmtiles on device while two generations coexist (**total**; +5.75 MB **incremental** over one pack) — and because Cache API entries never expire on their own and re-download is opt-in, the retained generation can persist **indefinitely** until the user taps the re-download or the deletion-consent control, or reverts with `?basemap_pmtiles=0`; a device at its storage ceiling keeps the old pack and an error message rather than a silent replacement; a worker fix propagates only after all tabs of a device close; four new Bulgarian strings enter the reviewed-wording surface; a retired version directory costs ~5.75 MB in the repo and deploy for one cycle (no repo-size cap exists, and first load is unaffected — the pack is never part of it).

**Neutral:** no change for live users while the flag is false (the worker is never registered); no dataset, Worker, or published artifact is touched; the `?basemap_pmtiles=0` revert path is unchanged and still removes every B2 cache, retained ones included.

## Rollout

Docs-first, then five small local commits per the execution plan, each with `node --check` + the unittest suite + a DevTools protocol gate, verified in a throwaway copy of the tree (never in the worktree). Petar signs (Gate 1), the Executor commits locally, an adversarial Auditor re-runs the gates, Petar reviews the diff (Gate 2) and pushes. The flag flip stays a separate signed step and must be preceded by a re-run of the real-device offline gate from `scratch/basemap_b2/stop_b2_local.md §15`. **Ordering constraint:** the side-feature framework in `scratch/additive_features_frame.md` (lines 103-106) must not launch into a world with an active service worker before this repair has landed — its own "the file enters `SHELL_ASSETS` in the same commit" discipline assumes the lifecycle decided here. **D7 scope:** the deploy-tree retention rule binds the *next* `BASEMAP_VERSION` bump, which is a separate signed cycle; this cycle lands only the policy and the widened (renamed) gate, which passes byte-for-byte on today's single-version tree.
